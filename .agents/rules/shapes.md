# 工作規則（自動載入，不是參考資料）

完整說明在 `docs/gemini-harness.md`。這裡只放**動作當下要認得的形狀**。
每一條的觸發都是「你剛寫下的那行字」，不是你的心理狀態。

- **S1 從沒開火過的守衛** — 剛寫下 `if`/`case`/`trap`/任何驗證 → 立刻造一個一定會違反它的輸入，看它紅。
- **S2 回 0 但沒生效** — 剛寫下「設定 X」→ 設定完讀回來。退出碼只證明指令被接受。
- **S3 沒跑過的旗標組合** — 剛寫下指令加旗標 → 原樣跑一次，usage error 比邏輯錯誤便宜十倍。
- **S4 換掉字，留下骨架** — 剛照別人的意見改了一行 → 把自己的 diff 當別人的 PR 讀，只問「這個改動弄壞了什麼」。
- **S5 抄來的收據** — 正要填收據欄 → 問「這條指令是誰決定要跑的」。全部來自別人＝你是抄寫員。
- **S6 知識宣稱冒充收據** — 收據欄沒有 `$` 也沒有 `rc=` → 那是推論，搬到推論欄。
- **S7 自省觸發器** — 剛寫下「當我覺得…就要…」→ 它不會開火，改成「當我剛寫下 X」。
- **S8 情緒結案** — 正要寫「完成／已徹底修正／我認輸」→ 那個位置屬於未驗清單。
- **S9 調的是尺，不是碼** — 正要編輯 `tests/`、`scripts/test.sh`、`.github/`，而任務不是測試工作 → 停。先回答「錯的是尺還是碼」，那段 diff 要單獨列出來當一個要被審查的主張。
- **S10 沒有對照組的「本來就紅」** — 測試紅了、正要判斷是不是既有問題 → `git worktree add --detach <base>` 跑同一支。不要用 `git stash`。

## 交付規範

1. 報告寫在 workspace 根目錄的 `report.md`，三欄：`## 觀察` / `## 推論` / `## 還沒驗`。
2. 觀察欄只收 transcript（`$ 指令` + 輸出 + `rc=`）。跑不出來就寫「收據：無」——**那是合法輸出，會過閘**。
3. 動到 `tests/`、`scripts/test.sh`、`.github/` 就要加 `## 尺的變更` 欄，逐條列出路徑並回答「為什麼錯的是尺不是碼」。
4. 未驗清單不得為空。
5. 禁止「完美／終極／無懈可擊／徹底解決／100%」這類完成宣告詞。

`Stop` hook 會在你想結束時跑 `scripts/harness-gate.sh report.md`。不過閘就結束不了。
